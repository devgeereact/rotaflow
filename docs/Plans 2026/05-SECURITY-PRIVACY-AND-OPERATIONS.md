# 05. Security, privacy, recovery and operations

RotaFlow will hold names, phone numbers, emails, pay rates, GPS positions at clock-in, leave reasons, emergency contacts and, today, links to documents such as DBS checks. That is enough to harm people if it leaks or is lost. The plan below protects it without turning a scheduling product into a compliance platform.

## 1. What is already solid (VERIFIED)

- RLS on every `public` table, enforced by `supabase/tests/database/rls_invariants.test.sql:35-77` (no table without RLS, no readable table without a policy, no grant to `anon` or `PUBLIC`).
- 145 `SECURITY DEFINER` functions, every one with `set search_path`. Membership checks tested in `definer_functions_check_membership.test.sql`.
- `anon` holds only schema usage and `preview_invite(text)` (`0075`, `0112:101`).
- Edge Functions: allowlisted CORS (`_shared/cors.ts:10-33`). User actions use the caller's JWT. The Stripe webhook verifies signatures and is idempotent (`0125`). AI and invites are rate-limited.
- Client: only public `VITE_*` values. Sentry with `sendDefaultPii: false`, a scrubber, EU region.
- Headers: CSP with `script-src 'self'`, nosniff, frame and referrer policies, HSTS. Leaving out `includeSubDomains` is a recorded decision (`.htaccess:88-97`), not a defect.
- Colleague privacy: `staff_profiles_visible` (`0150`) masks private fields from colleagues.
- Nightly encrypted backup, green every night since 5 September.

## 3. Privacy decisions in plain words

- **GPS:** collected only at clock-in and clock-out, never continuously. The clock-in screen says so in one sentence, with accuracy. Retained 36 months (`0092`), pending sign-off.
- **Leave reasons:** optional, with a hint not to include medical details. Never sent to AI.
- **Emergency contacts:** name, relationship, phone. Nothing medical.
- **Young workers:** if a sector needs it, record an age band ("under 18"), never a full date of birth.
- **Your data:** a "Your data" page in My account ([02](02-ORGANISATION-AND-STAFF.md) §7) routes into the existing GDPR case process.
- **AI:** server-side through OpenRouter only, IDs not names (S3), a manager always reviews before applying.
- **Marketing:** the website enquiry form never pre-ticks marketing consent.

Use the ICO's [processor guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/controllers-and-processors/controllers-and-processors/what-does-it-mean-if-you-are-a-processor/) as the review baseline. Never call the service "GDPR compliant". Name the controls instead.

## 4. Offline: what the product promises

As built (VERIFIED, `OFFLINE-SPEC.md`, `vite.config.ts:192-235`): the app shell is cached, Supabase reads are cached for 5 minutes, and exactly three actions queue offline: clock in or out (`ClockInPage.tsx:339`), leave (`LeavePage.tsx:341`) and swap (`SwapsPage.tsx:220`). The outbox is IndexedDB with idempotency keys (`0081`). The spec itself marks five of nine network conditions NOT TESTED.

The public promise becomes: **"Clock-ins, leave and swap requests can wait on the phone until the signal returns."** Not "works offline".

| Condition                              | Required behaviour                                                       |
| -------------------------------------- | ------------------------------------------------------------------------ |
| First visit with no signal             | Says a connection is needed to sign in. Shows no invented rota           |
| App opened offline with nothing cached | Shell opens with a clear "not available offline" state                   |
| Clock-in queued                        | "Waiting to send" on the button, with the time it was recorded           |
| Back online                            | Sends once. Shows "Sent" or the server's reason for refusing             |
| Session expired while queued           | Asks the same person to sign in, then sends. Never sends as someone else |
| Two tabs or two phones                 | No duplicate clock events                                                |
| App update while items are queued      | Queue survives the update                                                |
| Membership revoked                     | Queued writes are refused by the server, and the person is told          |

Add one Playwright test using `context.setOffline()` for clock-in, replay and expired session, and run the existing PWA project in CI with a local Supabase stack (GAP-072). Optional later (see [09](09-NEW-FEATURES.md) F9): a read-only copy of the person's own next shifts with "last updated" time.

## 5. Deployment and release safety

Keep the static `dist/` deploy. Each release records: commit, migrations applied, Edge Function versions, static build, and the service-worker version. A static rollback cannot undo a migration, so migrations stay backwards-compatible for one release. Define rollback and the post-release check before deploying. Watch, after release: error rate, outbox age, failed invites and notifications, webhook failures, backup freshness and one real clock-in.

Every release gate in CI stays as it is. Add the missing evidence: the PWA test in CI (above), one real-device check per release on iPhone and Android, and a measured performance test on a larger synthetic tenant (20 sites, 250 staff, 10,000 shifts, 50,000 clock events). Provisional budgets: first useful rota content within 3 seconds on a mid-range phone on 4G, filtering within 1 second. Measure, then set promises.

A skipped test is NOT TESTED, never PASS.
